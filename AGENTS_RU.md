# Паспорт проекта и регламент для ИИ-агентов: Linaro Releases

> **Проект:** BoardPort — Linaro Releases  
> **Организация:** [BoardPort](https://github.com/boardport) | **Репозиторий:** `boardport/linaro-releases`  
> **Миссия:** Безопасное архивное зеркало официальных релизов Linaro для отладочных плат  
> **Целевое хранилище:** GitHub Releases (`gh` CLI) | **Лицензия:** [MIT](./LICENSE)  

---

## 1. Организация контекста ИИ

Корневые файлы [`AGENTS.md`](./AGENTS.md) и [`AGENTS_RU.md`](./AGENTS_RU.md) служат базовым обязательным регламентом для всех ИИ-ассистентов.
Разработчики напрямую управляют, изолируют и настраивают вторичный контекст для своих инструментов:

- **Специализированные каталоги (`.(gemini|claude|cursor|continue|qwen|etc)/`):** Индивидуальный контекст конкретных ИИ-инструментов
  (промпты, инструкции, отчеты, дампы сессий). Эти каталоги изолированы и исключены из Git через `.gitignore`.
- **Файлы маршрутизации контекста:** Навигация и индексация внутри изолированных каталогов организуются через
  `.{ai}/README(_RU).md` или `.{ai}/AGENTS(_RU).md`. Специализированные инструкции дополняют корневой регламент.
- **Файл `.aiignore`:** Определяет ресурсы, строго исключенные из фонового сканирования и индексации
  (дампы памяти, сырые образы прошивок, архивы, временные кэши). Доступ к ним возможен только по прямому указанию.
- **Рабочая область (`tmp/`):** Все промежуточные загрузки, распаковка архивов и расчет хэш-сумм выполняются
  исключительно в неиндексируемом каталоге `tmp/`.

## 2. Архитектура релизов и хранения

- **Отсутствие тяжелых бинарников в Git:** Все тяжелые образы ОС, дампы разделов, rescue-пакеты и блобы прошивок хранятся в **GitHub Releases**.
- **Комплект ассетов каждого релиза:** При публикации релиза в GitHub Releases формируются:
  1. Бинарные архивы / файлы образов.
  2. Файл с контрольной суммой `.sha256` для каждого архива (или общий `SHA256SUMS`).
  3. Машинно-читаемый `manifest.json` с метаданными (версия, ядро, дата сборки, URL источников в Wayback Machine).
  4. Двуязычное описание релиза (Release Notes на GitHub) с двумя отдельными блоками (`[RU]` и `[EN]`).
- **Стратегия тегирования:** Плоские семантические теги для каждой платы и версии (например, `db410c-debian-18.01`, `db410c-rescue-17.09`).
  Глобальное версионирование репозитория не используется.
- **Инструмент публикации:** Публикация релизов выполняется вручную или через ИИ с использованием официальной утилиты GitHub CLI (`gh`).

## 3. Стандарты документации Markdown

- **Правила оформления:** Синтаксис и форматирование подчиняются `.editorconfig` и `.markdownlint-cli2.jsonc`.
- **Ограничение длины строк:** Не более 150 символов на строку (`MD013`).
- **Обязательный линтинг:** Команда `npx markdownlint-cli2` перед завершением работы должна возвращать `0 issues in 0 files`.
- **Зеркальная двуязычность:** Вся публичная документация ведется параллельно (`*.md` на английском и `*_RU.md` на русском).
- **Структура и наглядность:** Документация должна содержать лаконичные таблицы плат и прямые указания на релизы.

## 4. Стандарты Git и GitHub (`.github/`)

- Организационные политики, шаблоны задач, описания PR и процессы CI размещаются в [`.github/`](./.github/).
- Стандарты сообщений коммитов соответствуют соглашению Conventional Commits.
- **Правило Git-коммитов:** Создавать Git-коммиты разрешено **ТОЛЬКО по прямому указанию пользователя**.
